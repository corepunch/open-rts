# Plan 010 — Complete `dc_info_gen` sprite coverage; migrate Dropship to `A_` state actions

Follow-up from the combat-effects fix in commit `96712c1` ("Fix missing combat
effects and hidden-unit effect leaks; add combat/harvest/production tests").
Two items were explicitly deferred from that change because they are larger,
higher-risk, and need retail verification per
[`REVERSE_ENGINEERING.md`](../REVERSE_ENGINEERING.md) rather than being bundled
into a bug fix. This plan tracks them as standalone work.

---

## Part A — Regenerate `games/dark-colony/info.c` with full sprite coverage

### Problem

`games/dark-colony/info.c` and `games/dark-colony/info.h` are generated by
[`tools/dc_info_gen.c`](../tools/dc_info_gen.c) from the retail `.FIN`
animation data and `.SPR`/sprite sheets. The generator currently emits states
for only a subset of units/sprites, and known gaps exist:

- `tools/dc_info_gen.c` prints `dc_info_gen: missing FIN label %s` /
  `missing FIN draw part %s` / `missing sprite %s` warnings for cases it
  can't resolve — grep the tool for `"missing FIN"` and `"missing sprite"` to
  find current failure points before starting.
- Per [`AGENTS.md`](../AGENTS.md), the Exploiter walk cycle only has 2 `RUN`
  states (`RUN1`, `RUN2`) instead of the native 16 frames per facing.
- Alien units (Slug, Ortu, and some Grey variants) may be missing full
  direction/state tables even though their actor types now exist
  (`MT_DC_SLUG`, `MT_DC_ORTU` — added in issue DC-5).
- Muzzle-flash extraction (`fin_muzzle_for_body_row`,
  `fin_muzzle_for_sequence16_step` in `tools/dc_info_gen.c`) has a documented
  fallback path ("no BLAZ muzzle draw part for %s") that may silently skip
  some units.

### Goal

Regenerate `info.c`/`info.h` so every native unit/building sprite referenced
by `DARK_COLONY_ACTOR_TYPES` (in `games/dark-colony/g_game.c`) has complete,
correctly-oriented state tables (spawn/see/missile/death/muzzle as
applicable), matching retail FIN data — not placeholder or partial frame
counts.

### Constraints (read `REVERSE_ENGINEERING.md` first)

- **No unverified magic-number fixes.** Every frame count, direction count,
  or timing value must come from the actual `.FIN`/`.SPR` data, not from
  eyeballing a screenshot until it "looks right".
- **Preserve every finding.** Document confirmed/inferred/disproven/unknown
  facts about each unit's animation layout in `docs/DC_EXE_FINDINGS.md` as
  you go, not only in chat/terminal output.
- Run `build/bin/test_dark_colony_sprite_layout` after regenerating and keep
  it green; extend it if the regeneration reveals more layout invariants
  worth asserting (e.g. per-unit expected frame counts).
- Regenerate with:
  ```sh
  make dark-colony-info
  ```
  (wraps `tools/dc_info_gen` — see the `dark-colony-info` Makefile target).
- Diff the regenerated `info.c`/`info.h` against the current committed
  version before committing; a regeneration that silently drops or reorders
  existing correct states is a regression, not progress.

### Suggested steps

1. Run the generator against `data/DCOLONY` and collect every
   `dc_info_gen: missing ...` warning into a checklist.
2. For each missing/incomplete unit, find the actual FIN label naming
   convention used for its full frame set (compare against a unit that
   already generates correctly, e.g. Trooper `TRSC`) and fix the label/frame
   lookup in `tools/dc_info_gen.c` accordingly.
3. Regenerate, diff, and confirm frame counts against native `.SPR` frame
   totals (`tools/anim_extract` or direct `.SPR` header inspection can help
   verify counts independent of the FIN interpretation).
4. Add or extend headless tests (`tests/dark-colony/test_*.c`) asserting the
   previously-missing states now exist and resolve to valid sprite/frame
   pairs (mirror the existing
   `assert_dark_colony_exploiter_work_states`-style tests in
   `tests/dark-colony/test_game_model_headless.c`).
5. Update `docs/DC_EXE_FINDINGS.md` with what was confirmed/fixed and what
   remains unknown (e.g. any unit still missing full coverage and why).

## Part B — Migrate the Dropship's hand-rolled timing to `A_` state actions

### Problem

`games/dark-colony/p_spec.c` implements dropship approach/unload/depart as a
bespoke `Dropship` struct with `elapsed_ms` counters and a hand-written
phase-transition table (`DropshipPhaseDef`, `dropship_phase_defs[]`,
`update_dropship`), entirely separate from the Doom-style
`state_t`/`mobjinfo_t`/`A_*` action system the rest of the engine uses (see
`AGENTS.md` → "Game and Network Architecture" and `play/actor.h`).

Concretely, today:
- `Dropship.elapsed_ms` is a raw millisecond counter, not the `tics`-based
  state countdown every other animated entity uses.
- `dropship_frame_at()` manually indexes into `DropshipAnimation.frames[]`
  instead of going through `state_t.nextstate` chaining.
- `sync_dropship_parts()` directly spawns/positions visual-effect "parts"
  per frame instead of firing from a state's `action` callback
  (`StateAction`, e.g. `A_DC_MuzzleFlash`'s pattern).
- Phase completion callbacks (`dropship_approach_done`,
  `dropship_unload_done`, `dropship_depart_done`) are wired through a
  parallel `DropshipComplete` function-pointer table
  (`dropship_phase_defs[]`) instead of the state machine's `nextstate` +
  `action` fields.

This duplicate mechanism is exactly the pattern the codebase's own
conventions warn against (see the Dropship note already flagged in the
prior session's exploration): "it shall use `A_` functions not some custom
junk."

### Goal

Represent dropship approach/reposition/unload/depart as a normal
`mobjinfo_t`/`state_t` chain (spawnstate → seestate/missilestate-equivalent
→ deathstate-equivalent, reusing the existing `misc1` group-lock convention
where relevant), with `A_` action functions doing what
`sync_dropship_parts`/`dropship_*_done` do today. This should let the
dropship participate in the same `P_SetMobjState`/`P_Ticker` state-advance
loop as every other mobj, instead of a second, parallel ticker
(`update_dropship`) called from mission code.

### Suggested steps

1. Read `play/p_mobj.c` (`P_SetMobjState`, `P_Ticker`) and
   `games/dark-colony/p_inter.c` (`A_DC_*` examples) to confirm the exact
   contract a new `A_DC_Dropship*` action must satisfy (signature
   `void (statecontext_t *ctx, mobj_t *mo)`, side effects via `ctx`).
2. Decide whether the dropship becomes a real `mobj_t` (simplest — reuses
   `core.state_id`/`core.tics`/`P_SetMobjState` verbatim) or keeps a
   lightweight parallel struct that merely *reads* `state_t`/`mobjinfo_t`
   tables for timing instead of hand-rolled `elapsed_ms`. Prefer becoming a
   real `mobj_t` unless there's a concrete reason it can't be (e.g. it needs
   to exist before/after the normal unit array bounds, or needs multiple
   simultaneous "parts" that don't map to one `mobj_t`).
3. Define new states (e.g. `S_DC_DROPSHIP_APPROACH`, `S_DC_DROPSHIP_UNLOAD1..N`,
   `S_DC_DROPSHIP_DEPART`) in `games/dark-colony/info.c`/`info.h` (by hand or
   by extending `tools/dc_info_gen.c` if the animation frame data comes from
   FIN too — check whether dropship animation data is native FIN or
   engine-authored before deciding).
4. Port `spawn_dropship_part`/`sync_dropship_parts` logic into an `A_`
   action fired per-frame via the normal `tics`/`nextstate` chain, and port
   `dropship_approach_done`/`dropship_unload_done`/`dropship_depart_done`
   into actions fired on entering the next state (matching the
   `A_DC_TrooperAttackStart`/`A_DC_Fall` pattern already in
   `games/dark-colony/p_inter.c`).
5. Remove `update_dropship`, `DropshipPhaseDef`, `dropship_phase_defs[]`, and
   the manual `elapsed_ms` bookkeeping once the state-driven path covers the
   same behavior.
6. Add a headless test (`tests/dark-colony/test_dropship_lifecycle.c` or
   similar, following the `tests/rts_model_test.h` helpers used in
   `test_combat_and_harvest.c`) that drives a scripted dropship delivery
   end-to-end and asserts: approach → unload (payload units spawn) →
   depart, using state-machine ticks rather than reading `elapsed_ms`
   directly (that field should no longer exist once migrated).
7. Manually re-verify a dropship mission (e.g. HUMAN03, which uses scripted
   reinforcements per issue #2) still delivers units and despawns correctly:
   ```sh
   env SDL_VIDEODRIVER=dummy OPEN_RTS_DEBUG_SCRIPT=1 \
     build/bin/dark-colony --check data/DCOLONY SCENARIO/HUMAN/HUMAN03.MAP
   ```

### Acceptance criteria (both parts)

- `make clean && make all` builds all four game binaries.
- `make test` passes end-to-end.
- `games/dark-colony/info.c`/`info.h` cover every unit referenced in
  `DARK_COLONY_ACTOR_TYPES` with complete, retail-verified frame/direction
  counts (no placeholder 2-frame walk cycles where retail has more).
- The Dropship no longer has a bespoke `elapsed_ms`/`DropshipPhaseDef`
  ticker; its animation and phase transitions are driven by
  `state_t`/`mobjinfo_t`/`A_*` actions like every other mobj.
- New/updated headless tests cover both changes.
- `docs/DC_EXE_FINDINGS.md` records what was confirmed, inferred, or left
  unknown during the `info.c` regeneration.
